# 用例管理

用例管理是 Argus 的检测工程中心，提供 Sigma 检测规则的集中化导入、创建，并可将规则发布到 Kibana（Elastic）和 Splunk，同时包含字段映射管理、Kibana 同步工具和发布历史审计记录。

**导航路径：** `Data Pipeline → Detection`

> **本指南范围：** 规则管理、发布与字段映射配置。涉及批量上传、规则删除、发布、同步等会改变系统数据的操作，应按团队变更管理流程执行。Detection 页面还包含 **Notable Events** 和 **Risk Config** 标签页，本指南不涉及。

![Detection / Rule Library 页面]({{ '/assets/images/use-case-management/detection-list.png' | relative_url }})

## 快速导航

| 页面 | 路径 |
|---|---|
| Rule Library | Data Pipeline → Detection → Rule Library 标签页 |
| Field Mappings | Data Pipeline → Detection → Field Mappings 标签页 |
| Publish History | Data Pipeline → Detection → Publish History 标签页 |

如需了解已启用规则如何转化为日志源覆盖率和 ATT&CK 覆盖率，请参见[检测覆盖]({{ '/zh/detection-coverage/' | relative_url }})。

## Rule Library（规则库）

规则库是管理 Sigma 检测规则的主界面，支持搜索、过滤、批量导入、手工创建、与 Kibana 同步以及导出。

### 搜索与过滤

- **搜索框**（`Search rules, tags, or data sources`）— 按规则名称、标签或数据源过滤，按回车键重新加载。
- **Product 过滤器** — 缩小到某一产品的规则（取自规则的日志源），默认 `All Products`。
- **Severity 过滤器** — 规则库中出现的严重级别，通常为 critical、high、medium、low，默认 `All Severities`。
- **Status 过滤器** — 规则库中出现的状态（如 draft），默认 `All Statuses`。
- **Reset** — 清除搜索、过滤、排序和分页设置。

过滤、排序和分页状态会在当前浏览器会话内保留，因此打开某条规则后返回时依然有效。仪表盘上的 ATT&CK 热力图也通过同样的机制，打开按技术或战术预先过滤的列表。

表格上方显示规则数量（`Showing n / m rules`），列如下：

| 列 | 说明 |
|---|---|
| **Rule Name** | 规则标题；点击行可打开规则 |
| **Severity** | critical / high / medium / low |
| **Status** | Sigma 规则状态，如 draft |
| **Log Source** | 来自 Sigma `logsource` 的 product、service 和 category |
| **Profile** | 编译规则所用的字段映射 Profile |
| **Tags** | Sigma 标签，包括 `attack.*` 标签 |
| **Elastic** | `Kibana Enabled`（已发布且已启用）、`Published`（已发布但未启用）或 `Not Published` |
| **Splunk** | 每个 Splunk 发布器一个标签：`<发布器>: Enabled` / `Disabled`，未同步时显示发布状态，或 `Not Published` |

### 导入规则

| 方式 | 说明 |
|---|---|
| **GitHub URL** | 粘贴 Sigma 规则 YAML 原始文件的 URL（如 `https://raw.githubusercontent.com/.../rule.yml`），点击 **Import**；平台抓取并导入后打开该规则 |
| **Upload → Upload Files** | 选择一个或多个本地 `.yml` / `.yaml` Sigma 规则文件 |
| **Upload → Upload Folder** | 选择一个文件夹，上传其中所有 `.yml` / `.yaml` 文件 |

上传完成后，会提示创建、更新和跳过的规则数量。

工具栏的其他操作：

| 按钮 | 说明 |
|---|---|
| **Delete (n)** | 确认后（`Delete n selected rules?`）删除已勾选的规则 |
| **Sync with Kibana** | 从 Kibana 拉取已发布规则的启用状态（见下文 Sync with Kibana） |
| **Export** | 下载当前规则库 |
| **New Rule** | 打开规则编辑器 |

### 手工创建规则

![New Rule 弹窗]({{ '/assets/images/use-case-management/new-rule-modal.png' | relative_url }})

1. 点击 **New Rule**。
2. 填写字段：
   - **Rule ID** — 唯一标识符（如 `aws_cloudtrail_root_login`）
   - **Tags** — 可选；输入标签后按回车（如 `attack.execution`、`attack.t1059.001`）。标签会修改下方 YAML 的 `tags:` 列表
   - **Sigma YAML** — 完整的 Sigma 规则定义
3. 点击 **OK**。

> **保存前建议：** 由检测工程师复核 YAML 语法、字段引用和严重级别。规则错误往往在发布时而非创建时暴露。

### 规则命名规范

遵循包含数据源、检测行为和实体的命名方案：

```
<数据源>_<行为>_<实体>
```

示例：
- `aws_cloudtrail_root_login`
- `windows_defender_malware_detected`
- `linux_sudo_privilege_escalation`

### 规则详情

点击某条规则可打开详情页。**Back to List** 返回规则库；**Edit** 重新打开 YAML 编辑器。

<!-- TODO screenshot: assets/images/use-case-management/rule-detail-elastic.png (rule detail page with Kibana Detection Rule card and Tags card) -->

页眉显示规则标题、严重级别、状态、版本和描述，并提供发布目标选择器：**Elastic** 或 **Splunk**。

| 区域 | 说明 |
|---|---|
| **Log Source**、**Mapping Profile** | 规则适用的日志源，以及编译规则所用的字段映射 Profile |
| **Tags** 卡片 | 编辑规则标签；修改后出现 **Save** 和 **Reset** |
| **Kibana Detection Rule** 卡片（Elastic 目标） | 发布状态和 Kibana 操作（见下文） |
| **Cron Job / Schedule** 卡片（Elastic 目标） | Kibana 规则的 **Run every**（`1m` 至 `1h`）和 **Lookback**（如 `now-16m`） |
| **Detection** 标签页 | **Sigma**、**ES|QL**（无法生成 ES|QL 时为 **Lucene**）和 **Versions** |

在 **ES|QL** 标签页中，可以设置规则的索引模式、编辑查询（**Save ES|QL** 会将其标记为 `manual`；**Regenerate from Sigma** 恢复为 `autogenerated`），并配置 **Kibana Detection Actions**（连接器模板和动作参数；**Save Configuration**）。在 **Versions** 中选择某个版本并点击 **Roll Back Selected Version** 即可回滚；每个版本都会列出变更类型和变更摘要。

#### 标签与 ATT&CK

**Tags** 卡片决定[检测覆盖]({{ '/zh/detection-coverage/' | relative_url }})的结果。先添加 `attack.<tactic>` 标签（如 `attack.execution`），再添加技术标签，如 `attack.t1059.001`。保存标签修改后会出现如下警告：

> Tag changes are saved locally (ATT&CK coverage already uses them) but not yet published to Kibana. Click Publish to Kibana to sync.

即标签仅保存在本地（ATT&CK 覆盖率已使用这些标签），尚未发布到 Kibana，需点击 **Publish to Kibana** 同步。

### 发布到 Kibana

选择 **Elastic** 目标。平台的 Kibana 连接必须已配置。

1. **Preview in Kibana**（或 Kibana 卡片中的 **Rule Preview**）会对规则执行预览并显示结果。
2. **Publish to Kibana** 在 Kibana 中创建规则（已存在则更新），并在 Publish History 中记录一条 `publish`。
3. 如果规则以未启用状态发布，会弹出对话框 **Rule published but not enabled** —— *This rule is saved in Kibana as disabled, so it will not run or count toward detection coverage. Enable it now?* 请选择 **Enable now** 或 **Later**。

**Kibana Detection Rule** 卡片显示状态（`Enabled`、`Published but Disabled` 或 `Not Published`）、Sigma Rule ID 和 Kibana Rule ID，并提供：

| 按钮 | 作用 |
|---|---|
| **Rule Preview** | 在 Kibana 中预览规则 |
| **Enable** / **Disable** | 修改规则在 Kibana 中的启用状态（已发布时可用） |
| **Delete Kibana Rule** | 确认后从 Kibana 删除该规则；Sigma 规则仍保留在规则库中 |

> 只有已启用的规则才会在 Kibana 中运行并计入检测覆盖率。

### Sync with Kibana

如果有人直接在 Kibana 中启用、停用或删除规则，规则库就会与 Kibana 不一致。规则库工具栏上的 **Sync with Kibana** 用于将其对齐。

1. 点击 **Sync with Kibana**。
2. 确认对话框：*Kibana is treated as the source of truth. Enabled state of published rules is overwritten, and rules no longer found in Kibana are marked unpublished and disabled (not deleted). Each change is recorded in the rule's version history.*（以 Kibana 为准；已发布规则的启用状态会被覆盖；Kibana 中已不存在的规则会被标记为未发布并禁用，但不会删除；每项变更都会记入规则的版本历史。）
3. 查看结果提示：`Synced with Kibana: n state change(s), n no longer in Kibana, n unchanged`。

行为说明：

- 仅检查已发布过的规则；每条规则按规则 ID 与其 Kibana 规则匹配。
- 启用状态不一致时，规则库采用 Kibana 中的值。
- Kibana 中已不存在的已发布规则会被标记为**未发布并禁用**，但不会被删除。
- 每项变更都会在该规则的 **Versions** 历史中保存为一条 `kibana_sync` 记录。
- **安全检查：** 如果 Kibana 完全没有返回规则，而规则库中存在已发布规则，同步会终止并报错（`Kibana returned no rules; refusing to unpublish n published rule(s). Check the Kibana space and API key permissions.`），不做任何更改。
- 需要具备修改集成的权限，否则请求会被拒绝。

当 **Elastic** 列或覆盖率数字与 Kibana 不一致时，请执行该操作。

### 发布到 Splunk

在规则上选择 **Splunk** 目标，可将其发布为 Splunk 计划任务型保存搜索（告警）。

**前提：** 在 `Data Pipeline → Integrations` 下已配置 Splunk Rule Publisher 集成。若不存在，面板会显示 *No Splunk Rule Publisher configured* 和 **Integrations** 按钮。保存、发布和启用需要修改集成的权限；删除需要删除集成的权限。

**流程：** **Save Configuration** → **Compile SPL** → **Publish to Splunk**。

1. 选择 **Splunk publisher** 并填写配置（见下表），点击 **Save Configuration**。
2. 点击 **Compile SPL**，在 **SPL** 标签页中预览生成的查询。
3. 点击 **Publish to Splunk**，确认 *Publish this rule to Splunk in disabled state?*。配置已保存且没有未保存的修改时才可发布。
4. 在 Splunk 中检查保存搜索后，点击 **Enable**（确认 *Enable this scheduled Splunk alert and its actions?*）。

> **规则始终以未启用状态发布。** 只有当发布状态为 `synced`、自发布以来 Sigma 规则和配置均未变化、没有未保存的修改且规则尚未启用时，**Enable** 才可用。

| 字段 | 规则 |
|---|---|
| **Source index** | 必填；字母、数字、`_`、`.`、`-`；最长 64 个字符（默认 `main`） |
| **Sourcetype** | 可选；字母、数字、`_`、`:`、`.`、`-`；最长 100 个字符 |
| **Cron schedule** | 必填；有效的五段式 cron 表达式（默认 `*/5 * * * *`） |
| **Lookback (minutes)** | 1 至 10080（默认 15） |
| **Trigger comparison** | `greater than`、`less than` 或 `equal to` |
| **Result count** | 0 至 1,000,000（默认 0） |
| **Once per search** | 默认开启；使用 **Suppression** 时必须开启 |
| **Suppression (seconds)** | 0 至 86400 |
| **Webhook URL** | 可选；仅限 `https`，不得包含凭据、查询串或片段 |
| **Email recipients** | 可选；最多 10 个有效邮箱地址 |

其他按钮：

| 按钮 | 作用 |
|---|---|
| **Disable** | 在 Splunk 中停用该保存搜索 |
| **Refresh Status** | 重新读取 Splunk 中的保存搜索并更新状态 |
| **Delete Remote Rule** | 删除 Splunk 保存搜索及绑定关系（*The Sigma rule will be kept*，Sigma 规则保留） |

发布状态：

| 状态 | 含义 |
|---|---|
| `draft` / *Not configured* | 已保存配置但尚未发布，或尚无配置 |
| `synced` | Splunk 保存搜索与已发布内容一致 |
| `drifted` | 保存搜索在 Argus 之外被修改，或与已发布配置不一致 |
| `missing` | Splunk 中已不存在该保存搜索 |
| `pending` / `pending_sync` | 操作正在进行或结果不确定；在进行其他更改之前请先点击 **Refresh Status** |

标签会显示 `Enabled` / `Disabled` 及已发布的版本号；当规则或配置在发布后发生变化时，会出现 **Unpublished changes** 标签。面板的 **SPL**（最近编译或最近发布的查询）、**Sigma** 和 **Versions** 标签页均为只读。

> 当仍有规则绑定到某个发布器时，不能修改其 host、app 和 owner，也不能删除该发布器。请先删除远程规则。

## Field Mappings（字段映射）

字段映射将 Sigma 的标准字段名转换为查询后端（Splunk、Elasticsearch）实际使用的字段名。映射质量直接决定规则能否命中正确日志。

**导航路径：** `Data Pipeline → Detection → Field Mappings`

![字段映射列表]({{ '/assets/images/use-case-management/field-mappings.png' | relative_url }})

### 映射结构

| 列 | 说明 |
|---|---|
| **Profile** | 映射配置分组，如 `aws_cloudtrail` 或 `windows_sysmon` |
| **Sigma** | Sigma 规则中使用的规范字段名 |
| **Splunk** | Splunk 中对应的字段名 |
| **Elastic ECS** | Elasticsearch ECS 中对应的字段名 |
| **Multivalue** | 若 Elastic 字段可包含多个值，则为 `Yes` |
| **Elastic Index Patterns** | 该映射适用的 Elasticsearch 索引范围 |
| **Actions** | **Edit** |

工具栏提供 **Search mappings**、**Upload Mapping Files**、**Upload Mapping Folder**、**Download CSV Template**、**Export**、**Delete Selected**、**New Mapping** 和 **Refresh**。

### 创建字段映射

![New Mapping 弹窗]({{ '/assets/images/use-case-management/new-mapping-modal.png' | relative_url }})

1. 点击 **New Mapping**（或先点击 **Download CSV Template**，填写后上传以批量导入）。
2. 输入 **Mapping Profile**。
3. 输入 **Sigma Field** 名称。
4. 填写对应的 **Elastic ECS Field** 和/或 **Splunk Field**。
5. 如适用，勾选 **Elastic field is multivalue**（见下文）。
6. 指定 **Elastic Index Patterns**，每行一个或以逗号分隔（如 `logs-*`、`winlogbeat-*`）。可选的 **Category**、**Data Source** 和 **Event Category** 字段用于对映射分类。
7. 点击 **OK**。

### 多值字段

部分 ECS 字段是数组（如 `process.args` 或 `host.ip`）。对此类映射勾选 **Elastic field is multivalue**（CSV 列名为 `elastic_is_multivalue`，取值 `true` / `false`）。规则编译为 ES|QL 时，对多值字段的 `field == "value"` 比较会被改写为 `MATCH(field, "value")`，从而匹配该字段的任一元素。未标记为多值的字段仍按常规使用 `==` 比较。

### 映射最佳实践

- 为每个数据源创建独立的 Profile（`aws_cloudtrail`、`windows_sysmon`、`linux_auditd`）。
- 在发布规则前，对照实际索引模板验证字段名。
- 确认 Elastic Index Pattern 覆盖实际存储数据的索引。
- 将数组字段标记为多值，使等值判断可匹配任一元素。
- 新增映射后，重新发布受影响的规则以应用更新后的字段转换。

## Publish History（发布历史）

发布历史提供每次规则发布操作的完整审计记录，涵盖 Kibana 和 Splunk。

**导航路径：** `Data Pipeline → Detection → Publish History`

![发布历史页面]({{ '/assets/images/use-case-management/publish-history.png' | relative_url }})

### 列说明

| 列 | 说明 |
|---|---|
| **Rule** | 规则名称 |
| **Target** | 发布目标：Kibana 为 `elastic-dev`，Splunk 发布器为 `splunk:<发布器 ID>` |
| **Action** | 执行的操作：`publish`、`enable`、`disable` 或 `delete`；Splunk 的状态刷新记录为 `refresh` |
| **Status** | `success`，或 `failed`、`pending`、`pending_sync` 等非成功值 |
| **Message** | 详细结果信息；发布失败时优先查看此列 |
| **Time** | 发布时间戳 |

使用 **Refresh** 重新加载列表。**Sync with Kibana** 产生的变更不会出现在此处，而是显示在相关规则的 **Versions** 中，类型为 `kibana_sync`。

### 发布失败诊断

当发布状态显示失败时：

1. 阅读 **Message** 列——通常会指明具体错误（YAML 无效、字段映射缺失、目标不可达）。
2. 检查规则的 Sigma YAML 语法是否正确。
3. 确认规则中引用的所有字段在对应 Profile 中均有映射。
4. 确认目标后端（Kibana 或 Splunk）可达，且集成配置正确。
5. 对于 Splunk，若状态为 `pending` 或 `pending_sync`，请打开该规则的 Splunk 面板并点击 **Refresh Status**。

## 用例管理检查清单

在发布新检测规则前，请逐项核对：

- [ ] 数据源已接入并正在采集数据（Data Pipeline → Integrations）
- [ ] 规则使用的每个 Sigma 字段均有对应的字段映射，数组字段已标记为多值
- [ ] 规则名称遵循 `数据源_行为_实体` 命名规范
- [ ] 规则带有 `attack.<tactic>` 和 `attack.t…` 标签，以便计入 ATT&CK 覆盖率
- [ ] 严重级别设置合理——避免将所有规则默认设为 Critical
- [ ] 规则已在测试/预发布索引上验证误报率
- [ ] 发布到 Kibana 后规则已启用（或你有意选择了 **Later**）
- [ ] 批量操作（删除、批量上传、发布、Sync with Kibana）已获得变更管理审批
